# 多轮对话逻辑和上下文管理说明

## 📋 整体流程

### 1. 对话历史管理结构
```python
conversation_history = {model_name: []}  # 为每个模型维护独立的对话历史
# 格式：[{"role": "user", "content": ...}, {"role": "assistant", "content": ...}, ...]
```

### 2. 每轮的处理流程

#### 第一轮（Round 1）
1. **构建当前消息** (`current_user_msg`):
   - 包含完整提示词模板（用户画像描述 + 题型提示 + 问题文本）
   - 包含图片（如果有）
   - 示例：
     ```json
     {
       "role": "user",
       "content": [
         {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}},
         {"type": "text", "text": "[用户画像提示词]\n[题型提示词]\n问题：xxx\n选项：..."}
       ]
     }
     ```

2. **调用API**:
   - `messages = conversation_history[model_name].copy()` （第一轮为空）
   - `messages.append(current_user_msg)` （包含完整提示词）
   - 发送完整提示词给模型

3. **保存到历史**（已优化）:
   - 保存精简的user消息（只包含问题文本，不包含提示词模板）
   - 保存精简的assistant消息（只包含提取的答案或前500字符）

#### 第二轮及以后（Round 2+）
1. **构建当前消息** (`current_user_msg`):
   - 仍然包含完整提示词模板（⚠️ **这是冗余的**）
   - 不包含图片（已检查历史，避免重复）

2. **调用API**:
   - `messages = conversation_history[model_name].copy()` （包含之前所有轮的精简历史）
   - `messages.append(current_user_msg)` （⚠️ **又加了完整提示词**）
   - 发送给模型：精简历史 + 完整提示词

3. **保存到历史**（已优化）:
   - 保存精简版本

## 🔍 Token冗余问题分析

### 当前的情况

**每轮都发送完整提示词模板的原因**：
- 用户画像描述（beginner/retail/expert等）：每轮都发送
- 题型提示词（单选题、多选题等说明）：每轮都发送
- **原因**：因为 `conversation_history` 中保存的是精简版本（只有问题文本，不包含提示词模板），所以从第二轮开始，如果不发送完整提示词，模型就看不到用户画像和题型信息

2. **历史消息中已保存精简版本，但调用API时仍使用完整版本**
   - `conversation_history` 中保存的是精简版本（只有问题文本）
   - 但调用API时的 `current_user_msg` 包含完整提示词
   - 导致第二轮到N轮时，仍发送完整的提示词模板

### 已优化的部分

✅ **图片处理**：只在第一轮添加图片，后续轮次不再重复
✅ **历史保存**：保存到 `conversation_history` 时已精简（只保存问题文本和答案）

## 💡 优化建议

### 当前的设计权衡

**为什么每轮都发送完整提示词？**
- 因为 `conversation_history` 中保存的是精简版本（只有问题文本）
- 如果从第二轮开始只发送精简问题，模型会丢失用户画像和题型信息
- 所以每轮发送完整提示词是**必要且合理的**

### 可能的优化方向

**方案1：在历史中保存用户画像和题型信息（一次性）**

在第一轮保存完整提示词到历史中（只保存一次），后续轮次使用精简问题：
- 第一轮：发送完整提示词，保存完整提示词到历史
- 第二轮及以后：只发送精简问题（因为历史中已经有角色信息了）

**优点**：后续轮次可以节省约200-500 tokens/轮
**缺点**：历史消息会变长，但只增加一次（第一轮）

**方案2：使用简短的提示词（而非完整模板）**

从第二轮开始，只发送简短的提示，例如：
- "继续以金融专家的角色回答"
- "这是一道单选题"
而不是重复完整的用户画像描述

**优点**：可以节省部分token
**缺点**：可能不如完整提示词清晰

**方案3：保持现状**

如果模型能很好地在多轮对话中保持上下文，当前的实现已经足够合理。

## 📊 Token消耗估算

假设一个3轮对话：

### 当前方式（每轮发送完整提示词）
- Round 1: ~1000 tokens（完整提示词 + 问题 + 图片）
- Round 2: ~800 tokens（精简历史 + 完整提示词 + 问题）
- Round 3: ~1000 tokens（精简历史 + 完整提示词 + 问题）
- **总计**: ~2800 tokens

### 优化后（仅第一轮发送完整提示词）
- Round 1: ~1000 tokens（完整提示词 + 问题 + 图片）
- Round 2: ~400 tokens（精简历史 + 问题）
- Round 3: ~400 tokens（精简历史 + 问题）
- **总计**: ~1800 tokens

**节省**: 约 1000 tokens（约36%）
